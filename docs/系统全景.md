# 系统全景

> 这是一张面向使用者和接手开发 Agent 的“地图”：解释系统现在如何工作、哪些能力已经上线、哪些只有地基，以及后续建设的边界。代码细节以实际实现和 `开发交接.md` 为准。

---

## 一、一句话理解这套系统

这是一个住在用户自己电脑上的个人 Agent 操作系统：用户用自然语言与 Codex、Claude Code 等 Agent 交流，Agent 调用本地工具管理 Markdown 数据；桌面浮窗提供随手查看和操作，git 在两台机器之间保存历史并自动同步。

它不是一个自己训练的 AI 模型，也不是一个中心化在线服务。系统的长期价值在于三件事：

1. 数据由用户持有，离开某个模型或工具仍然可读、可迁移。
2. 同一套业务动作可被对话 Agent 和桌面浮窗共同复用。
3. 隐私边界、状态机和验收流程被写进代码与文档，而不是依赖 Agent 临场记忆。

## 二、系统如何流转

### 对话入口

```text
用户说人话
   ↓
外部 Agent 理解意图
   ↓
actions.py 执行业务动作和校验
   ↓
vault.py 读写 Markdown
   ↓
数据仓自动 commit / 后台同步
```

Codex / Claude Code 提供语言理解和开发能力；本仓提供稳定的“手”（actions）、“账本”（vault）和“规矩”（schema / 手册 / 状态机）。因此可以替换 Agent 工具，而不需要迁移数据或重写核心业务。

### 浮窗入口

```text
Electron 浮窗
   ↓ JSON 命令
os_api.py
   ↓
同一套 actions.py
   ↓
同一套 Markdown 数据仓
```

对话和浮窗不会各自维护一套业务规则：勾任务、日常打卡、开发验收和同步最终都落到同一工具层。

## 三、四层架构的真实进度

| 层 | 作用 | 当前已经上线 | 仍待建设 |
|---|---|---|---|
| 数据层 | 保存结构化、可追溯的数据 | Vault CRUD；task/worklog/planning/decision/rule schema；routine；父子任务、依赖、常驻、日志 | 个人生活域正式启用；更多类型按真实需求增加 |
| Agent 层 | 理解意图并调用工具完成工作 | actions 高层动作；管家手册；通用专项 Agent 的提议、决策、验收闭环；开发与实习攻略两个执行器 | planning/decision 完整动作；更多真实专项；Agent 复盘与更强的自主规划 |
| 心跳层 | 在没有用户主动询问时定时工作 | 数据每 2 分钟同步；代码每 30 分钟检查；冲突检查；跨日与启动时补日志 | 按 `due/scheduled` 主动提醒；周期复盘和其他用户通知 |
| 治理层 | 约束 Agent 权限、决策和记忆 | 隐私边界；schema 与状态机；低电不可逆决策钩子；开发验收协议；候选规则库 | 电量状态机、token 预算、规则毕业/废弃机制、治理钩子全面接线 |

所以当前最准确的描述是：**数据层与日常工具已可用，Agent 层已有可靠手脚但智能仍依赖外部 Agent，心跳和治理均为部分完成。**

## 四、数据模型：现在有哪些“账本”

核心记录之间的关系：

```text
planning 目标 ──拆解──▶ task 要做的事 ──完成──▶ worklog 做过的事
                              │                         │
                              ├──参考 decision          └──沉淀 rule 候选
                              └──引用 rule ◀─────────────────────┘

routine 日常 ──按日打卡──▶ dailylog 每日任务日志（派生视图）

knowledge 学习对象 ──展开──▶ knowledge-note 摘要 / 思考 / 疑问 / 联想
```

| 记录 | 用途 | 实现程度 |
|---|---|---|
| `task` | 任务、子任务、依赖、优先级、专注、常驻与开发流程 | ✅ 动作 + 浮窗闭环 |
| `worklog` | 记录完成事实和过程；任务完成时可自动生成 | ✅ 动作闭环 |
| `routine` | 每日打卡，支持一天多次的进度型日常 | ✅ 动作 + 浮窗闭环 |
| `planning` | 目标、里程碑与任务引用 | 🟡 schema 与校验已完成，高层动作待补 |
| `decision` | 记录选项、可逆性、精力与选择理由 | 🟡 schema、校验和治理钩子已完成，写入闭环待补 |
| `rule` | 保存候选、已验证或废弃的经验规则 | 🟡 新增/查询已上线，毕业与自动复盘待补 |
| `dailylog` | 按机器生成的每日任务快照和打卡记录 | ✅ 自动生成与补偿 |
| `knowledge` | 论文、播客、书籍等内容的想学/学习中/已学队列、优先级与成长统计 | ✅ 动作 + 独立浮窗闭环 |
| `knowledge-note` | 挂在具体学习内容下的多条摘要、思考、疑问、联想与行动 | ✅ 追加动作 + 浮窗查看/录入 |

任务还有三个 Agent 协作中间状态：

```text
todo → pending_start → in_progress
                         ├→ pending_decision → in_progress
                         └→ pending_review → done
```

它让各专项 Agent 的“想做什么、卡在哪里、做完了什么”都进入用户可见、可打回、可验收的系统，而不是留在一次性聊天里。执行器注册表声明角色与授权根：系统开发 Agent 可处理系统任务；带根的专项 Agent 只能处理本机 `.env` 配置的私有任务子树，不能靠修改调用参数越权。

实习攻略 Agent 与主管家、系统开发 Agent 是并列的独立对话，不是任何一个角色的临时子 Agent。它复用上述任务闭环，简历与岗位材料则写入 `.env` 指向的仓外工作区；路径解析会拒绝绝对路径和 `..` 越界。`system-code` 只保存代码、协议和脱敏 fixtures。

## 五、浮窗现在承担什么

Electron 浮窗已经是可用界面，不再是静态 mock。它提供：

- 五分类下的无限层级任务树与父子折叠。
- 专注区：用户当前推进的叶子任务与不同专项 Agent 的任务分别成栏。
- 今日待办区：位于专注区下方，作为总待办与专注之间的北京时间当日缓存；普通待办点星加入，
  可进入专注或移回总待办，专注任务也可退回今日。
- 依赖未满足的任务延后并弱化展示，但不粗暴隐藏。
- 敏感节点的中性遮罩，并由父节点向整棵子树继承。
- 日常栏、进度型打卡、昨日完成区和常驻任务。
- 通用 Agent 验收窗口：待开始、待决策、待验收可直接处理，并显示实际执行器；任务正文支持安全的 Markdown 渲染。
- 独立知识库窗口：展示想学队列、正在学习、已学习统计与内容类型筛选；可调整优先级和状态，点开条目查看或追加具体笔记。
- 同步冲突红条、5 秒数据刷新、全局快捷键、托盘/程序坞恢复入口。

浮窗是本地视图，不承担大模型推理。需要理解长文本、拆解任务或开发代码时，仍由对话 Agent 处理。

## 六、双机与隐私边界

### 三个仓，各守一条边界

```text
system-code     框架、schema、文档、脱敏 fixtures
      ↕          两机共享；可自动快进更新

work-vault      真实任务、日志、规则等当前工作数据
      ↕          两机并行读写；私有 git 仓双向同步

personal-vault  情绪、健康、画像等真正生活隐私
                 仅个人机；工作机不得 clone / pull
```

需要特别区分两件事：

- **显示层隐身**：工作机只显示 `source_machine=work` 的记录，个人机是全量聚合端。这能减少误触和旁人窥屏，但文件仍可能存在于两机共享的 `work-vault`。
- **物理隔离**：真正不能进入工作机的生活隐私必须放入 `personal-vault`。只有分仓才是硬边界。

当前 `personal-vault` 真实生活域尚未正式启用。因此在完成分仓路由前，不应把“工作机看不见”误解成“工作机没有这份数据”。

### 双机并行写如何避免丢数据

1. 新记录 id 带机器后缀，如 `task-demo-001w` / `task-demo-001p`，避免两机同时编号撞同一路径。
2. actions 写入后立即本地 commit，并在后台 fetch / merge / push；断网不阻塞本地写入。
3. 浮窗启动后和每 2 分钟主动同步，拉取另一台机器的修改。
4. 两机修改同一文件同一处时，本机版留作正本，对方版保存为 `.conflict-<sha>` 副本并随仓同步。
5. 浮窗显示冲突提醒；最终内容需要 Agent 或用户对比两份后人工合并。

冲突保双份的目标是“宁可多一份，也不静默丢失”。它不是自动判断哪一份业务内容正确。

## 七、已经能完成的一天

现在的实际体验是：

```text
早上 / 启动浮窗
  → 自动同步两机数据
  → 补齐关机期间遗漏的每日任务日志
  → 展示专注任务、今日待办、总待办树、日常与昨日完成

白天
  → 对 Agent 说“记个任务 / 我开始做 / 卡住了 / 做完了”
  → Agent 调 actions 写入数据，自动校验并同步
  → 浮窗里可勾任务，在总待办 / 今日待办 / 专注中三层流转，给日常打卡

专项 Agent 工作时
  → Agent 只在其授权任务根中提议下一项工作，用户批准
  → 需要选择时进入待决策
  → 完成后进入待验收，用户通过或打回
  → 业务产物写入该 Agent 配置的仓外工作区

跨日
  → 自动生成分机任务日志；若当时未运行，下次启动补偿生成
```

还不能声称做到的目标体验是：“任务到下午三点时系统主动弹出提醒”“每周自动阅读全部历史并自主提炼规则”“根据精力自动完成整套规划”。这些分别属于下一阶段的心跳、Agent 智能和治理建设。

## 八、后续路线与 YAGNI 边界

近期优先级应由已出现的真实问题驱动：

1. 用本地私有任务或脱敏样例持续验证专项 Agent 的授权根、验收闭环与外挂工作区。
2. 实现按时间提醒待办，让心跳层第一次真正主动面向用户。
3. 再根据实际使用补 planning / decision 动作、规则治理与 Agent 自我复盘。
4. 在隐私路由成熟后正式启用 personal-vault 生活域。

当前明确不提前建设：

- 不因为“将来可能有多个域”就先造通用插件体系。
- 不因为“将来可能自治”就先引入常驻大模型服务或中心数据库。
- 不因为有多个执行器就复制业务逻辑；外部 Agent 统一调用 actions，差异只进入执行器注册表、授权根和外挂工作区配置。
- 不为没有真实使用反馈的功能堆字段、层级和抽象。

原则仍是：**先把一个真实痛点做成完整闭环，出现第二、第三个相似场景后，再抽取公共机制。**
